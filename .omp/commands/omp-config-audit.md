# OMP config audit

`~/.omp/agent/autogenerated.yml` is Nix-generated from
`config/llm-agents/oh-my-pi/config.nix` (deep-merged with any
`mdarocha.llm-agents.oh-my-pi.settings` override) — see
`config/llm-agents/oh-my-pi/default.nix`. Nix never writes or touches
`~/.omp/agent/config.yml`; both wrapper binaries (`omp`, `omp-nosandbox`) load
`autogenerated.yml` first and `config.yml` last via `PI_CONFIG_FILES`, so
anything the user changes through OMP's own settings UI lands in `config.yml`
and always wins.

That also means changes made through the UI live only on this one machine's
`config.yml`, untracked by git. This audit finds settings there that look
like a deliberate, durable preference — not one-off or machine-specific state
— and, with approval, folds them into `config.nix` so they become the shared
default across every machine on next `home-manager` activation. It also
checks the repo's own declared values in `config.nix` against the currently
pinned `omp` version's schema, since a setting can go stale with no runtime
drift at all — the tool renamed or removed it upstream and is now silently
ignoring what the repo declares.

## Phase 0 — resolve the active configuration

```bash
source scripts/lib.sh
echo "$CONFIGURATION"
```

Same detection `nix run .#apply` uses. Trust it over guessing from hostname/env.

## Phase 1 — load the repo value and the live value

Repo value — build the exact file the next activation would write, rather
than re-reading `config.nix` by eye (an override in
`mdarocha.llm-agents.oh-my-pi.settings` for this `$CONFIGURATION` could change
it):

```bash
nix build --impure --no-link --print-out-paths --expr '
  (builtins.getFlake (toString ./.)).homeConfigurations."'"$CONFIGURATION"'".config.home.file.".omp/agent/autogenerated.yml".source
'
```

Read the resulting store path with `cat`/`yq -o=json` — this is **repo**.

Live value — `~/.omp/agent/config.yml` (expand the real `$HOME`, not a
sandboxed one; if this path isn't reachable, check whether you're running in
a sandbox and ask the user to disable it before continuing). Parse with
`yq -o=json` — this is **current**. If the file doesn't exist yet, stop: there
is nothing to audit.

## Phase 2 — diff at top-level-key granularity

Compare **current** against **repo**, key by key (recursing into nested
objects such as `theme.*`, `retry.*`):

- keys present in **current** but absent from **repo**, or present in both
  with a different value → the user set this through OMP's own UI; not yet
  reflected in the repo.
- keys present in **repo** matching **current** → already promoted; nothing
  to do.

There is no backup file and no "last apply clobbered a local edit" case to
reconcile here — Nix never writes `config.yml`, so every difference is a
one-directional promotion candidate, not a conflict.

## Phase 3 — decide what's worth adopting

- Skip secrets, tokens, credentials, session ids, cache paths, timestamps, or
  other locally-generated/ephemeral state — never propose committing those.
- Skip anything plausibly specific to this one machine or `$CONFIGURATION`
  variant rather than a general preference (target
  `mdarocha.llm-agents.oh-my-pi.settings` in the matching
  `flake-modules/home-configurations/<name>.nix` for those, not the shared
  `config.nix`).
- Keep candidates that look like a deliberate, durable preference set through
  OMP's own settings UI.
- Exclude keys already at OMP's own built-in default. Get the *built-in*
  defaults from an isolated config dir rather than the user's own — the
  installed wrapper still requires `autogenerated.yml` to exist (it's a
  strict `PI_CONFIG_FILES` overlay), so pre-touch an empty one in the scratch
  dir:

  ```bash
  scratch=$(mktemp -d)
  mkdir -p "$scratch/.omp/agent"
  touch "$scratch/.omp/agent/autogenerated.yml"
  HOME="$scratch" PI_CODING_AGENT_DIR="$scratch" omp-nosandbox config list --json
  ```

  This lists effective values/types/descriptions but omits enum choices —
  useful for confirming a key's default, not for enumerating valid values.
- Before checking any of this, skip a key outright if a prior audit already
  recorded a decision for it — see the "recording decisions" step in Phase 6.

## Phase 4 — check the repo's own declared values for obsolete/removed keys

Independent of any live drift: check every key `config.nix` declares against
what the currently pinned `omp` version actually still accepts. Renamed or
removed settings are typically ignored silently, not rejected, so this needs
an explicit schema check rather than diffing live files.

1. Resolve the exact deployed version before consulting any schema — never
   check against `oh-my-pi`'s `main` branch. `omp` is packaged by the
   `llm-agents` flake input (`numtide/llm-agents.nix`): read
   `nodes.llm-agents.locked.rev` from `flake.lock`, then read
   `packages/omp/hashes.json` in `numtide/llm-agents.nix` at that exact
   commit for the pinned upstream `oh-my-pi` tag/version.
2. Fetch `packages/coding-agent/src/config/settings-schema.ts` from
   `github.com/can1357/oh-my-pi` at that exact release tag — the tool's own
   documented single source of truth for every setting path, type, default,
   and (for enums) the full valid `values` list. Cross-check against
   `docs/settings.md` and `docs/config-usage.md` at the same tag.
3. Flag any `config.nix` key path the schema no longer defines. Before
   proposing it obsolete, search the schema for an equivalent setting under a
   different path/name — renames usually keep the same value set (grep the
   old value among the candidates' enum options, not just the key name).
4. An unrecognized key is a defect, not a preference: apply the fix directly
   in Phase 6 without routing it through Phase 5's `ask` gate, unless the
   replacement value is genuinely ambiguous — then ask like any other
   candidate. Report what was renamed/removed and its replacement in the
   final summary either way.

## Phase 5 — ask before touching anything

For every surviving promotion candidate from Phase 3, use the `ask` tool
(batch related ones) showing: key path, current repo value (or "unset"),
proposed new value from `config.yml`, and confirmation it'll be added to
`config.nix`. Unanswered/declined candidates stay untouched.

Non-interactive/headless sessions have no `ask` tool available: present the
same information in the chat reply instead, batched into one list, and treat
the user's next reply as the answers.

## Phase 6 — apply approved changes

1. Add or update the approved key in `config/llm-agents/oh-my-pi/config.nix`,
   in the section matching its existing grouping comments (appearance,
   model, interaction, context, memory, tools, tasks, providers, composer,
   shell, sharing) — add a new one if none fits.
2. Re-run the Phase 1 build for the changed `$CONFIGURATION` and confirm the
   new value is present in the rebuilt `autogenerated.yml`.
3. For every candidate the user declined or asked to leave unmanaged, append
   a line to the comment block at the bottom of `config.nix`:

   ```nix
   # omp config audit decisions (see .omp/commands/omp-config-audit.md)
   # These comments are durable audit state; future runs must preserve them.
   # - <key path>: intentionally left unmanaged; skip in future audits.
   ```

   Keep one such block per file, appending new lines to it rather than
   duplicating the header. Future audits must check this block before
   re-flagging a key — treat it the same as a declined candidate and skip it
   without re-asking. These comments record state that is otherwise unavailable
   to future audits, so they satisfy the repo's comment policy. Keep the header
   intact when appending.

## Phase 7 — commit to main

Follow `skill://commit` for staging/message conventions. User-invoked, so
committing is expected without asking again — but confirm
`git branch --show-current` is `main` first; this workflow only touches
`config/llm-agents/oh-my-pi/config.nix`, so switching
to `main` should be safe. Stop and ask if `main` isn't checked out and the
working tree has unrelated pending changes. Do not push.
